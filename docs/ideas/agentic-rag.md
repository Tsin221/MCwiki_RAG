# Agentic RAG 未来方案

状态：预期方案，当前暂缓实施

更新时间：2026-07-29

## 问题陈述

如何为公开用户提供一个可信度优先的 Minecraft 知识助手，使其能够根据已有证据
自主决定是否继续检索、是否改写查询、是否访问受信任的官方站点核验，并最终生成
带有可追踪来源的回答？

## 已确认的产品约束

- 面向公开用户，而不是仅供内部或个人使用；
- 回答可信度优先于最低延迟和最低调用成本；
- 本地知识库优先；
- 联网检索只允许 Minecraft Wiki 和 Minecraft/Mojang 官方站点；
- 本地数据清洗、分块和向量生成继续使用本地模型与本地服务；
- Agent 决策、证据判断和最终回答使用云端 LLM；
- 联网获取的内容只作为当前请求的临时证据，不自动写入本地知识库；
- 当前先完成本地混合检索 MVP，不急于实现本方案。

## 推荐方向

采用“本地优先、按需联网、证据驱动循环”的单 Agent 工作流。未来可以使用
LangGraph 管理显式状态、条件分支、检索循环和调用预算，但第一版不拆成多个 Agent。

Agent 先调用本地 BM25 + Qdrant 混合检索。当本地证据不完整、可能过时、相互冲突，
或问题明确要求核验当前版本信息时，才调用受域名白名单约束的联网工具。联网结果经过
临时正文提取、去重、相关片段选择和安全检查后，与本地证据一起交给云端 LLM 回答。

联网内容不需要走离线清洗、分块、向量化和持久化流程，但不能把原始网页直接交给
模型。请求期仍需进行必要的证据处理，以保证相关性、引用准确性和安全性。

## 预期工作流

```text
接收问题
   ↓
问题分类与时效判断
   ↓
本地 BM25 + Qdrant 混合检索
   ↓
证据充分性与冲突检查
   ├─ 充分 ───────────────────────┐
   │                              ↓
   └─ 不充分 / 可能过时 / 有冲突 → 受限联网检索
                                      ↓
                                临时证据处理
                                      ↓
                                再次检查证据
                                      ├─ 继续检索或改写查询
                                      └─ 达到完成或停止条件
                                              ↓
                                      云端 LLM 生成回答
                                              ↓
                                      返回回答、引用与说明
```

## 预期状态

未来 LangGraph 状态至少包含：

- 原始问题；
- 标准化后的问题；
- 问题类型及是否具有时效性；
- 本地检索轮次和结果；
- 联网检索轮次和结果；
- 已确认的事实与对应证据；
- 尚未解决的证据缺口；
- 证据冲突；
- 当前调用次数、时间和 Token 预算；
- 停止原因；
- 最终回答及引用。

## 预期节点与职责

### 1. classify_question

- 判断问题是否涉及当前版本、最近更新或其他易变化信息；
- 判断问题是否需要拆分成多个子问题；
- 不直接回答事实问题。

### 2. retrieve_local

- 调用本地 BM25 + Qdrant + RRF 检索；
- 返回统一结构的候选证据；
- 保留 chunk ID、标题、正文、来源和检索分数。

### 3. evaluate_evidence

- 判断关键事实是否都有证据支持；
- 检查证据是否来自权威来源；
- 检查不同来源之间是否冲突；
- 输出明确的证据缺口，而不是只输出模型自报的“置信度”。

### 4. plan_next_search

- 针对证据缺口改写查询；
- 决定再次查询本地知识库还是联网；
- 检查调用预算和停止条件。

### 5. search_trusted_web

- 只访问配置的域名白名单；
- 在工具层强制限制域名、协议、重定向和响应大小；
- 返回网页标题、规范 URL、抓取时间和正文。

### 6. prepare_web_evidence

- 去除导航、脚本、广告和其他无关内容；
- 提取与问题相关的片段；
- 合并重复信息；
- 标记来源和抓取时间；
- 将网页中的指令性文本视为不可信数据，防止提示词注入。

### 7. generate_answer

- 只依据已收集证据回答；
- 为关键事实提供对应来源；
- 明确区分确定事实、存在冲突的信息和无法确认的信息；
- 达到预算上限但证据仍不足时，明确说明无法可靠回答。

## 联网触发条件

满足以下任一条件时，可以考虑联网：

- 问题包含“最新”“当前”“最近”“现在版本”等时效性表达；
- 本地检索没有覆盖问题中的关键事实；
- 本地检索结果相互冲突；
- 本地资料可能早于问题所涉及的 Minecraft 版本；
- 用户明确要求从官方来源核验；
- 证据评估节点给出了可以通过官方资料补足的明确缺口。

不能仅因为 Agent “想查看更多信息”就联网。每次联网都必须对应一个明确的证据缺口。

## 证据充分性规则

不能只依赖 LLM 输出的主观置信度。至少需要检查：

- 回答中的每个关键事实是否有直接证据；
- 来源是否在允许范围内；
- 来源是否与问题所问版本对应；
- 多个来源是否相互冲突；
- 引用片段是否真正支持对应表述；
- 是否存在只能推测、无法确认的内容。

## 安全与公开服务边界

- 域名白名单必须由联网工具强制执行，不能只写进系统提示词；
- 禁止访问本机地址、内网地址和非 HTTP(S) 协议，防止 SSRF；
- 限制重定向次数、响应大小、抓取时间和单次请求数量；
- 网页内容始终视为不可信输入；
- 不执行网页中的指令，不向网页提交密钥或用户隐私；
- 云端模型只接收回答所需的证据片段，不上传整个本地知识库；
- 日志避免保存云端 API 密钥、完整用户隐私和不必要的网页正文；
- 对公开接口实施请求频率、并发量和总预算限制。

## 关键假设与验证方式

- [ ] 本地混合检索能够覆盖大多数稳定知识问题：使用固定评测集统计本地检索的
  Recall@K，并记录需要联网的问题比例。
- [ ] Agent 能稳定识别时效问题与证据缺口：建立包含稳定问题、时效问题、冲突问题
  和无答案问题的路由评测集。
- [ ] 白名单站点能够补足本地知识库的主要时效缺口：对真实问题记录联网成功率、
  有效证据率和无法覆盖的内容类型。
- [ ] 云端 LLM 能正确遵守证据边界并生成准确引用：人工检查关键事实—证据对应关系，
  评估引用准确率和无依据陈述比例。
- [ ] 多轮检索带来的可信度收益足以抵消延迟和成本：对比单轮、两轮和三轮检索的
  正确率、耗时与 Token 消耗。

## Agentic RAG MVP 范围

本方案进入实施阶段后的最小版本包括：

- 一个 LangGraph 状态图；
- 一个云端 LLM，同时承担规划、证据评估和回答生成；
- 本地混合检索工具；
- 一个受域名白名单约束的联网检索工具；
- 证据缺口驱动的查询改写；
- 最多约三轮检索的硬限制；
- 完整的停止原因、引用和失败说明；
- 快速回答与深度核验使用同一图，通过预算参数区分。

## 当前不做

- **不立即引入 LangGraph**：先完成并评测本地检索工具，否则 Agent 没有可靠底座；
- **不拆分多个 Agent**：Planner、Researcher、Verifier 多 Agent 会增加成本和调试难度；
- **不把联网内容自动写入知识库**：避免实时请求引入重复、污染和不可追踪的持久数据；
- **不开放任意互联网访问**：公开服务必须限制来源和攻击面；
- **不允许无限循环检索**：所有循环必须受次数、时间和 Token 预算约束；
- **不使用单一“置信度分数”决定停止**：停止条件必须结合证据覆盖与冲突检查；
- **不在第一版实现复杂用户记忆或多轮任务编排**：先验证单次知识问答的可信度。

## 实施前置条件

以下本地混合检索 MVP 完成并通过评测后，再启动本方案：

1. 查询文本的本地 Ollama embedding（已完成）；
2. Qdrant Top-K 语义召回（已完成）；
3. BM25 与 Embedding 双路召回（已完成）；
4. RRF 排名融合（已完成）；
5. FastAPI `/search`（已完成）；
6. 10～20 个带正确来源的本地检索评测问题（已完成，共 15 题）；
7. 对召回率、排序质量、响应时间和失败行为有基线数据（首次基线已完成）。

## 开放问题

- 允许访问的 Minecraft Wiki 和官方域名具体清单；
- 云端模型供应商、模型及成本上限；
- 公开服务的单请求时间、检索轮次和 Token 预算；
- “快速回答”和“深度核验”是否都需要在第一版提供；
- 引用需要展示网页级来源、段落级片段，还是两者都展示；
- 当 Wiki 与官方资料冲突时，默认采用何种优先级；
- 是否允许用户明确关闭联网或强制官方核验。
