# 任务 04：多子问题拆分、检索与完整回答

## 任务目标

对包含多个明确要点的问题建立有上限、可审计的处理流程，使每个要点都有检索状态、回答内容
和引用，解决“证据存在但答案遗漏条件”的问题。

建议分支：`codex/multifacet-answering`

依赖：任务 01、03 已合并。

## 背景

苦力怕问题同时询问爆炸条件和多类掉落。当前证据包含大部分内容，但回答没有完整解释音乐唱片
的击杀条件。这属于生成完整性问题，而不是主来源漏召回。

## 推荐流程

```text
原问题
  → 识别 1～4 个回答要点
  → 原问题先检索一次
  → 仅对证据不足的要点补充检索
  → 合并并组织证据
  → 按要点逐项回答和引用
  → 输出前检查是否有未覆盖要点
```

这是一条有固定上限的管道，不是自主 Agent 循环。

## 范围

1. 定义 `QuestionFacet` / `QuestionPlan` 等明确数据契约；
2. 支持单问题和多要点问题；
3. 每个要点记录 `sufficient / insufficient` 及使用的证据 ID；
4. 最多一次补充检索，最多 4 个要点；
5. 生成提示中要求按要点输出，缺证据时逐项说明；
6. 在 SSE 对外契约不破坏兼容性的前提下保留诊断信息。

## 规划器选择

执行者应先比较两种小样本方案：

- 确定性规则：基于问号、并列词、“哪些/分别/以及”等生成要点；
- 一次结构化模型规划：严格 JSON，解析失败时回退为单要点。

只有结构化规划在 v2 多子问题集上明显更准，且延迟可接受时才作为默认。不能让规划失败导致
整次请求失败。

## 运行边界

- 最多 4 个要点；
- 最多 1 次额外模型规划调用；
- 最多 1 轮补充检索；
- 不允许联网；
- 不允许模型自由决定无限重试；
- 总字符预算仍使用现有配置；
- 单问题默认保持现有快路径。

## 建议文件边界

- 新增 `code/rag_question_plan.py`；
- 新增相应测试；
- 修改 `rag_api.py` 的回答编排；
- 修改 `rag_answer.py` 的上下文或提示契约；
- 扩展评测输出以记录要点覆盖、调用次数和延迟。

前端协议若无需展示计划，不要增加 UI 实现细节。

## 验收标准

- [ ] v2 多子问题的要点识别准确率经人工复核不低于 95%；
- [ ] 多子问题要点覆盖率不低于 95%；
- [ ] 每个已回答要点至少有一个有效引用；
- [ ] 无证据要点明确标记不足，不使用模型记忆补齐；
- [ ] 原 18 题正确性、忠实度和拒答率不退化；
- [ ] P95 总延迟相对当前基线增长不超过 30%；
- [ ] 每题调用次数、补检次数和停止原因进入评测输出；
- [ ] 规划失败、补检失败和模型超时均有测试。

## 重点回归案例

- 苦力怕：唱片和头颅条件必须分别回答；
- 铁傀儡：生成方式与保护对象都必须覆盖；
- 末影珍珠：移动效果与副作用都必须覆盖；
- 无答案题：不能因为拆分后某个词命中就转为猜测回答。

## 交接重点

报告单问题与多问题各自的延迟和调用数。若完整性收益只来自更长答案，应说明成本，不能只报
覆盖率。
