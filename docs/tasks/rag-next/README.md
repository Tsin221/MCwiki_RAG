# MCwiki RAG 下一阶段任务包

更新时间：2026-09-23

包含背景、边界、验收标准和交接要求。执行者应先阅读本文件、自己的任务文档、
`PROJECT_STATUS.md` 和最新回归报告。

最新证据：`data/evaluation/answer_quality/REPORT-2026-09-22-reliability.md`。

## 执行波次

| 波次 | 任务 | 是否可并行 | 说明 |
|---|---|---|---|
| 1 | 01、02 | 可以 | 分别建立评测底座和诊断词法检索，不修改同一核心文件 |
| 2 | 03 | 否 | 使用任务 01 的评测口径，改进证据组织 |
| 3 | 04 | 否 | 在任务 03 的证据组织结果上增加多子问题流程 |
| 4 | 05 | 条件执行 | 只有评测证明分块导致漏证据或噪声时才做 |
| 5 | 06 | 否 | 汇总前面结果，运行统一回归并作技术决策 |

任务 01 和 02 可以从同一个 `main` 起点并行。其余任务应在前置任务合并后再开始，避免
不同分支同时改动 `rag_answer.py`、`rag_api.py` 和评测代码。

## 任务文件

1. `01-evaluation-v2.md`：建立可诊断的评测集 v2 与标注规范；
2. `02-bm25-diagnostic.md`：建立 BM25 专项题集并完成可复现的对照实验；
3. `03-evidence-assembly.md`：减少重复证据和无关历史块，提高上下文纯度；
4. `04-multifacet-answering.md`：让多子问题逐项检索、回答和引用；
5. `05-section-parent-child-prototype.md`：条件性验证章节分块与父子块；
6. `06-integration-quality-gate.md`：统一回归、人工复核和后续技术决策。

## 所有执行者共同遵守的规则

1. 不修改或覆盖 2026 年 7 月、9 月已有基线文件。
2. 不删除失败问题，不通过更改问题或标签掩盖退化。
3. 新实验使用新文件名，并记录数据集、配置、提示词和代码版本。
4. 每次只验证本任务提出的一个主要变量；不要顺手加入 Reranker 或 Agent 框架。
5. 不提交 `.env`、API Key、临时日志、IDE 配置或本地数据库副本。
6. 自动化测试通过后再运行真实模型评测；真实调用结果必须保存完整运行配置。
7. 若结果不优于基线，应保留实验报告并撤回默认行为，不得只提交“看起来更先进”的代码。
8. 每个执行者使用独立分支，建议名称见对应任务文档，并只提交自己的任务范围。

## 统一交接格式

每个执行者完成后应提供：

- 分支名和提交哈希；
- 修改文件清单；
- 执行过的验证命令及结果；
- 与基线逐项对比的指标；
- 失败案例和未解决风险；
- 是否建议合并，以及建议的下一任务输入。
